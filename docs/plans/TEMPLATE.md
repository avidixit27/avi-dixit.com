## Outcome

State the observable result and why it matters. Describe the finished state rather than the activity.

## Prerequisites and current state

- List dependency outcomes that must already exist.
- Identify repository facts and affected behavior to reconfirm before editing.
- Identify required access or decisions. Do not include credentials.

## Scope

- List the responsibilities and behavior included in this ticket.
- Name anticipated files or ownership areas when known.

## Non-goals

- List adjacent work intentionally excluded from the ticket.

## Deliverables

- List concrete code, configuration, documentation, or evidence the ticket will produce.

## Implementation plan

1. Give an ordered, decision-complete sequence.
2. Connect each step to its purpose and expected result.
3. Include migrations and compatibility handling when applicable.

## Acceptance criteria

- State independently observable pass/fail outcomes.
- Include relevant failure and accessibility behavior.

## Verification

List exact commands and manual scenarios available in the ticket's starting state. Distinguish automated checks, browser review, and unavailable future tooling. Do not claim unconfigured checks.

## Definition of done

- Implementation and documentation satisfy every in-scope acceptance criterion.
- Relevant available checks pass, and results or justified limitations are recorded.
- The diff contains only ticket scope and receives review.
- Architecture and agent guidance reflect any changed enduring or current-state facts.
- The PR and plan index contain the final status and links.
- Follow-up work is recorded without silently expanding this ticket.
